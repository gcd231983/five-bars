# Five Bars 4.0 — Consumer correction intake and editorial handling

**Status:** Public reader reports are supported through GitHub, but there is **no private customer support channel**, no guaranteed response time, no rewards program, and no automatic modification of the price catalog. This is not carrier customer service.

## Reader experience

1. From a plan, phone, research record or footer, open the [correction assistant](https://gcd231983.github.io/five-bars/report.html). The offer ID is filled from the published catalog when available.
2. Describe the problem (wrong advertised rate, first-bill/AutoPay fees, stock, port eligibility, terms, network/coverage or website behavior). Enter the date and a **public official carrier URL** when possible.
3. The draft remains local to the page and never enters the page URL, an analytics service, a Five Bars server, or an account database. Basic validation flags obvious personal information, but it is **not** a complete redaction tool.
4. Explicitly acknowledge that GitHub issues are public, preview the draft, copy it, open the [GitHub correction issue form](https://github.com/gcd231983/five-bars/issues/new?template=offer-correction.yml), paste it and submit only if comfortable sharing it.
5. A GitHub account is required. The public repo currently has **no private support mailbox**; do not provide private account details or choose an untrusted destination to circumvent this limitation.

**Never share:** account numbers, PINs, transfer secrets, names, payment-card data, identifiable checkout screenshots, subscriber addresses, phone numbers or IMEIs. A writer can accidentally paste private details despite the local validation. Review everything yourself before posting.

## Editorial correction workflow

**1. Triage:** Identify offer ID and category, distinguish reports about site function from carrier-rate claims, and check whether another open report already covers the same issue. Avoid treating repeat submissions as corroborated independent evidence.

**2. Review evidence:** Verify a selected public carrier page, Broadband Facts or official terms page, not merely HTTP availability, screenshots from unknown accounts or public comments. Confirm the **exact** handset/plan, line count, rate, AutoPay requirements, first bill, compulsory fees, expiration, portability, network, stock and financing/credit details. If verification is blocked, mark the outcome **not confirmed** rather than fabricating a value.

**3. Resolve material pricing contradictions:** If new official research conflicts with the catalog, create or update the dated source evidence record and preserve the price-conflict hold. Source observations and complete human checkout scenario attestations are separate records. Out-of-stock promotions are not automatically restocked because a link starts working. Reader reports never directly change the catalog, review ledger, or consumer ranking.

**4. Implement a supported fix:** Change only the affected fields, document the official source and observation date, update the price/switching tests, run catalog validation and full mobile/desktop browser CI, then merge after review. Independent human checkout verification requires the separate protected workflow and actual anonymized full-terms quote. Never create fictional reviews.

**5. Close the loop:** Reply publicly with a concise supported conclusion (corrected, duplicate, unable to confirm, not a Five Bars issue or further review required), link the commit/source when available, and close only when triage is complete. Never promise a response by a specific time without a staffed support program.

## Commercial readiness constraints

- No affiliate relationship is created by this workflow and reports must **never** influence paid rankings.
- Future paid referral links need clear, understandable disclosures **close to each compensated recommendation or link**, with actual signed agreements first. A general disclosure page alone is not sufficient.
- Any future private no-login reporting channel requires an owner-selected contact provider, moderation, abuse protection, consent/privacy updates, retention rules and controlled access before deployment.
- Do not display fabricated "tickets handled," satisfaction percentages, verified prices, subscriber counts or revenue. Gather actual measurements only if privacy safeguards and a legitimate operational process are in place.
